# SaaS 生產線
### 從興趣到收費產品的完整手冊 —— 以 Hookvox 真實上線經驗整理

> 這份手冊教你把自己的興趣、專業或想法，一步步變成一個真的能上線、真的能收費的產品。全程只需要一個工具：**Claude Code**——一個可以打字聊天的視窗，你不需要懂任何技術指令，用中文把事情講清楚就好。
>
> 老實話先講在前面：**這不是「打一句話 AI 就幫你生出一整個產品」的過程。** 真實的開發是「討論清楚 → 做一點點 → 試試看 → 發現壞掉 → 跟 AI 講清楚哪裡壞 → AI 修好 → 再試一次」，這樣來回很多次。這份手冊會誠實教你這整個過程。

---

## 怎麼使用這份手冊

**最推薦的用法：讓 Claude Code 直接讀這份檔案，邊看邊聊。**

1. 在你的電腦桌面新增一個新的資料夾，取一個你聽得懂的名字，例如「我的第一個產品」
2. 把這份檔案存到那個資料夾裡
3. 打開 Claude Code
4. 跟它說：「請你在桌面『我的第一個產品』這個資料夾工作，裡面有一份『SaaS產品開發引導包.md』，麻煩你先完整讀過一遍，讀完後當我的教練，一步一步帶我照著做，每次只講清楚現在這一步，做完確認我懂了再繼續下一步」

之後你就可以邊看這份文件、邊在 Claude Code 裡跟它聊「我現在卡在哪裡」，它會依照這份文件的內容，一步一步帶你把產品做出來。

## Phase 00 — 事前準備

### Claude 聊天 vs Claude Code，不是同一個東西

平常用的 Claude 聊天版，只會打字回答你，不會真的幫你做出東西。**Claude Code** 打開後也是一個打字聊天的視窗，差別是：你請它做什麼，它真的會幫你把產品做出來、存檔、打開給你看。這份手冊教的「給 AI 的指令」，指的都是打在 Claude Code 裡的話。

手機還沒辦法用 Claude Code 動手做產品，可以先用手機的 Claude 聊天版整理想法，回電腦前再打開 Claude Code。

### 模型怎麼選：Sonnet 用 90% 的時間，Opus 留給卡關時

- **Sonnet**（例如 Sonnet 5）：速度快、成本低，日常寫功能、修小問題都用它。
- **Opus**（例如 Opus 5）：想得更深但比較慢，留給「規劃整個產品架構」或「一個問題卡很久都想不通」的時候。

切換方式：Claude Code 視窗下方有個可以直接點選的小選單，不用打字下指令。之後模型改版了（Sonnet 6、Opus 6……），原則不變：輕量版日常用、進階版留給卡關時刻。

### 準備開發帳號

- **GitHub**：放程式碼的地方，像雲端硬碟但專門放程式，還能回到之前的版本。
- **Vercel**：把做好的產品「發布」成一個網址，讓大家都能打開使用。
- **Supabase**：幫你處理使用者登入/註冊、存資料，不用自己架資料庫。

三個都能先用 email 免費申請。不確定要準備什麼，直接把你的產品構想講給 Claude Code，請它列清單、一步步教你申請。

### 心理建設：這是一個不斷來回修正的過程

真實的開發永遠是這個迴圈：**先做一小部分 → 試試看能不能用 → 發現壞掉 → 把壞掉的狀況講給 AI 聽 → AI 修好 → 再測一次**，重複很多次。

真實案例：Hookvox（[hookvox-1yib.vercel.app](https://hookvox-1yib.vercel.app)）光是收費系統這塊，就經歷過使用者付了錢但系統忘記升級方案、後台一個小地方壞掉導致整頁打不開、同一個方案的可用次數兩個頁面顯示不一樣……每一個都是「發現問題 → 講清楚給 AI → AI 修好 → 再測一次」才解決的，到現在都還在持續調整。**發現東西壞掉不代表你做錯了，那是開發本來就會發生的事。**

### Checklist

- [ ] 已安裝 Claude Code，能正常打字對話
- [ ] 知道怎麼切換 Sonnet / Opus
- [ ] GitHub、Vercel、Supabase 帳號都申請好了
- [ ] 心理上接受「這是來回修正的過程」，不是一次到位

## Phase 01 — 找到你的產品

### 盤點你的興趣與專業

不需要一個「全世界都沒人做過」的點子，把你已經很懂、每天在用的知識和技能，包成一個別人可以直接用的工具就是好題目。

- **低價簡單的方向**：工作行事曆助理、Gmail 自動整理分類
- **高價複雜的方向**：AI 算命、爆款影片與貼文分析

### 難度與價格光譜

產品難度和售價通常一起往上升：

| 難度 | 範例 | 特性 |
|---|---|---|
| 簡單 / 低價 | 工作行事曆助理、Gmail 自動整理 | 功能單一，AI 能直接生成大部分程式碼，適合先練手 |
| 中等 / 中價 | 內容排程工具 | 需要一些判斷邏輯 |
| 複雜 / 高價 | AI 算命、爆款影片分析 | 需要更完整的資料設計，客單價與續訂率通常更高 |

誠實評估自己能投入的時間，選一個「做得完」的難度。

### 決定收費模式：一次性 vs 訂閱制

- **一次性收費**：付一次、用一次解決問題（例如 AI 算命單次解讀）。不用處理續訂、到期、額度週期，系統簡單很多，**適合第一個練手產品**。
- **訂閱制**：持續付費、持續使用（例如每天整理信箱）。客單價更高，但要處理額度、週期、到期、金流通知等更複雜的系統。

> 這裡先寫下你的決定，後面 Phase 05 依照你的選擇，只需要仔細看對應的那一段：
>
> **我的收費模式：______________**

### Checklist

- [ ] 已盤點自己的興趣/專業，列出至少 5 個候選點子
- [ ] 已依難度光譜挑出一個「做得完」的產品構想
- [ ] 已決定收費模式（一次性 / 訂閱制）

## Phase 02 — 驗證這值得做

### 設計驗證訪談，別問「要不要用 AI」

找 5-10 個目標客群做真實訪談，核心原則：**問「你現在怎麼解決」，不要問「你想不想要一個 AI 工具」**——後者幾乎每個人都會說想要，沒有參考價值。

- 他們現在花多少時間 / 金錢處理這件事？
- 他們有沒有試過付費買現成方案，後來為什麼沒繼續用？
- 如果解決了，願意付多少錢、多久付一次？

### 用手動服務先測試付費意願

在請 AI 動手做之前，先用最土的方式（Google 表單 + 人工處理）服務 3-5 個真實客戶，確認他們真的願意付錢。

> **常見錯誤**：還沒驗證付費意願，就先把整套產品、金流串接都做好了。先驗證「人會不會付錢」，再花時間讓 AI 做出來。

### Checklist

- [ ] 完成 5-10 個真實訪談
- [ ] 手動服務過 3-5 個真實付費客戶
- [ ] 確認轉換率與客單價值得投入開發

## Phase 03 — 討論網站長怎樣

### 先看一個真實案例：Hookvox

打開 [hookvox-1yib.vercel.app](https://hookvox-1yib.vercel.app) 逛 5 分鐘，留意：它有哪些頁面？每個頁面想讓你做什麼？色調和文字給你什麼感覺？

### 討論要有哪些頁面

Hookvox 的頁面組成（範例，不是標準答案）：

| 頁面 | 用途 |
|---|---|
| 首頁 | 給還沒註冊的人看，說明產品在幹嘛、多少錢 |
| 功能頁 | 實際使用產品核心功能的地方（登入後才看得到）|
| 方案頁 | 列出各種收費方案，按下去可以升級/購買 |
| 會員後台 | 看自己用了多少額度、帳號設定 |
| 帳單頁 | 付款紀錄、目前訂閱狀態、續訂/取消 |

不要照抄，這只是參考架構。**重點是學會怎麼跟 AI 討論這件事**，而且要有心理準備：AI 第一次給的規劃不會剛好是你要的，一定要來回討論幾輪才會定案，這很正常，就跟裝潢設計師畫平面圖也要跟屋主來回修改好幾次一樣。

### 討論風格與語氣

- **色調**：深色系（科技感、專業）還是淺色系（親切、輕鬆）？
- **語氣**：正式一點，還是像朋友聊天一樣輕鬆？
- **參考對象**：有沒有喜歡的其他網站，可以直接說「我想要有點像某某網站的感覺」

### 把討論結果變成一份規格文件

前面幾輪討論定案後，請 AI 把整個討論結果整理成一份完整的規格文件，這份文件會變成 Phase 04 的藍圖。就算有了規格文件，實際做出來後你一定還是會想調整——這是正常的。

### Checklist

- [ ] 已逛過 Hookvox 或其他真實案例當參考
- [ ] 已跟 AI 討論出頁面清單
- [ ] 已跟 AI 討論出視覺風格與語氣
- [ ] 已請 AI 整理成一份規格文件

## Phase 04 — 讓 AI 做出來

### 拿規格文件，請 AI 開始建立專案

把 Phase 03 的規格文件貼給 Claude Code，請它規劃技術架構、建立專案骨架。你不用懂技術細節，確認開發順序你能接受就好。

### 一次只教 AI 做一件事

不要一次要求「把整個產品做完」，把功能拆成一個一個小任務，**一次只做一件事、測過沒問題再進下一個**。描述功能時要講清楚：使用者會輸入什麼、系統怎麼處理、最後看到什麼結果。

### 請 AI 把做好的東西「打開」給你看

直接跟 Claude Code 說「幫我打開來看看」，它會處理背後的技術細節，給你一個網址，複製貼到瀏覽器打開就能看到實際畫面。這個階段只有你自己看得到，是正式上線前先自己試用的階段。

### 遇到問題，怎麼跟 AI 講清楚（最重要的技能）

你不需要自己會抓問題在哪，只需要學會把「壞掉的狀況」講清楚，一份好的問題描述要包含：

1. 你做了什麼操作
2. 你原本預期會發生什麼
3. 實際發生了什麼
4. 你看到的任何文字訊息（整段複製貼上，不要自己刪減）

> **常見錯誤**：只跟 AI 說「壞掉了」、「不能用」，AI 完全沒有線索判斷問題在哪。也可以直接說「你能不能自己檢查伺服器的紀錄」，Claude Code 有能力自己去查程式碼和紀錄。

### 讓 AI 幫你接資料庫與登入系統

使用者系統（註冊/登入）跟資料儲存，是幾乎每個產品都需要的基礎建設，讓 AI 用託管服務（例如 Supabase）串起來即可，不用自己從零寫。

### 串接收費：先求能收到第一筆錢

收費系統不用一開始就做到完美。一次性收費先用金流服務商的「快速結帳連結」就能收到第一筆真的錢；訂閱制則需要 Phase 05 的完整系統。

### Checklist

- [ ] AI 已依規格文件建立專案骨架
- [ ] 每個功能都是「一次一個」逐步完成並測試過
- [ ] 學會怎麼把 bug 講清楚給 AI（操作/預期/實際/完整訊息）
- [ ] 使用者登入與資料儲存已完成
- [ ] 已串上最簡單版本的收費流程，能收到第一筆錢

## Phase 05 — 金流與訂閱

這是整份手冊裡「地雷密度最高」的章節。依照你 Phase 01 選的收費模式，看對應的那一段。

### 【一次性收費】最簡單的做法

去申請金流服務商（例如藍新科技、綠界）的帳號，申請「快速結帳連結」，放在產品頁面上，使用者點下去付款。核心流程只有三步：**使用者點連結付款 → 你確認付款成功 → 開通權限**。一開始可以人工確認，量變大再考慮自動化。

### 【訂閱制】完整系統要注意的四件事

訂閱制比一次性收費複雜很多：

1. **資料要分兩張表**：Subscription（使用者現在的方案狀態）跟 Order（每一筆交易紀錄）分開存。因為付款通知可能失敗或重複，只有一張表出事後沒辦法回溯。
2. **金流通知要能處理失敗**：金流商付款成功後會發通知，每個處理步驟（驗證、解密、寫入資料庫）都要分開處理錯誤、並全部記錄下來，才查得出問題在哪。
3. **額度依週期計算，時間到自動重置**：例如月繳使用者，額度每 30 天重新計算，不是永久累加也不是永久不變。
4. **到期要自動處理**：訂閱到期後系統要自動把使用者降回免費方案，不用人工一個個改。

> **真實案例**：Hookvox 目前其實還沒做出真正的訂閱制——現在是使用者每個月要自己手動再付一次款，不是系統自動幫他續訂扣款。這是因為完整的自動續訂需要串接金流商的「定期定額」功能，複雜度又更高一層。剛開始做可以先做「使用者手動每期再付一次款」的簡化版，一樣算訂閱制的概念（有週期、有額度重置），只是還沒做到自動扣款而已。

### 通用觀念：金流通知容錯設計（不管哪種模式都要懂）

Webhook 是金流服務商跟你的系統之間的橋，橋斷了，使用者付了錢但方案沒更新，客訴會排山倒海而來。四件必做的事：

1. **每個處理階段獨立 try/catch**，不要共用一個 catch——驗證簽章、解密、JSON 解析、寫入資料庫，任何一步都可能單獨出錯。
2. **把每一次通知都記錄到獨立稽核表**：是否成功、失敗在哪個階段、原始內容。
3. **做冪等性檢查**：同一筆交易可能被重送，不能重複處理。
4. **加解密資料做容錯**：Key/IV 要 `.trim()`、驗證長度是否正確，失敗要記錄診斷資訊，不要只丟一句「解密失敗」。真實案例：環境變數尾端多了一個看不見的空白字元，導致解密全部失敗，錯誤訊息只顯示 `bad decrypt`，完全看不出真正原因。

隱藏陷阱：用 `formData.get()` 讀取加密資料時，`application/x-www-form-urlencoded` 格式會把 `+` 號解碼成空白字元，悄悄破壞資料。

### 額度與方案設計

免費額度是漏斗不是慈善——要讓使用者感受到價值，但不夠用到需要升級。**所有頁面顯示的額度數字要單一來源**：真實案例，某方案額度在程式碼裡是 150，但所有前台頁面都顯示 200，導致使用者投訴「明明說 200 為什麼扣到 150 就不能用」。

### Checklist

- [ ] 已依照自己的收費模式（一次性/訂閱制）選對應的做法
- [ ] Order 和 Subscription 分成兩張表（訂閱制才需要）
- [ ] Webhook 各處理階段有獨立錯誤處理與記錄
- [ ] Webhook 有冪等性檢查
- [ ] 加解密函式對 Key/IV 做過 trim 與長度驗證
- [ ] 有獨立稽核表記錄所有付款通知
- [ ] 有 admin 工具可以手動同步使用者訂閱狀態，且不受時間窗口限制
- [ ] 所有頁面顯示的額度/價格數字來自同一個設定檔

## Phase 06 — 測試與除錯（上線後）

### 建立管理後台：你的儀表板

產品上線、有真實使用者後，需要一個「只有你能進去」的管理頁面，至少要有：

- 使用者查詢（email 找到人，看方案、用量、付款紀錄）
- 手動修復工具（系統出狀況時一鍵修正，**不要限制時間範圍**，避免「明明有訂單卻修不了」）
- 操作紀錄（誰在什麼時候做了什麼操作）

### 前端容錯：一個小功能壞掉，不該讓整頁都打不開

如果一個頁面要同時讀取好幾筆資料才能顯示完整畫面，用 `Promise.all` 的話任何一筆失敗整頁就當機。應該用 `Promise.allSettled`，讓每個區塊獨立顯示成功或失敗。

### 建立你的「使用者說東西壞了」標準處理流程

1. 去金流商後台查這筆交易狀態是否為「成功」
2. 去自己系統的紀錄表查有沒有收到通知
3. 找出失敗在哪個階段
4. 用管理後台手動修復，先讓使用者能用
5. 請 AI 修好根本原因，避免下一個人也遇到

### Checklist

- [ ] Admin 後台有使用者查詢、手動同步、稽核紀錄三項基本功能
- [ ] 前端平行請求用 `Promise.allSettled`
- [ ] 建立好「付款未生效」的標準排查 SOP
- [ ] 定期檢查稽核表，主動抓出失敗但使用者還沒抱怨的個案

## Phase 07 — 行銷與銷售

### 早期通路：從既有信任關係開始

不要一開始就砸錢投廣告，先從已經有信任關係的地方開始：LINE 社群、IG 帳號、既有客群，轉換率遠高於冷流量。

### 定價心理學

- **早鳥優惠製造急迫感**：限時、限量比「長期折扣」更能促成當下決定。
- **方案分級對應真實使用情境**：中間一定要有一個對大多數人剛好夠用的主力方案。
- **免費試用額度是第一個轉換入口**，不是終點站。

### 用周邊商品增加營收來源、分散風險

多一個獨立收入來源（例如電子書、課程）能增加營收，也能在金流出狀況時證明業務不是只靠那一個管道。可以直接用金流服務商的快速結帳連結，不需要自己開發付款流程；在多個頁面用一致但不干擾主流程的方式露出。

### Checklist

- [ ] 第一波客戶來自既有信任通路，不是冷启動廣告
- [ ] 方案定價有清楚的早鳥/限時邏輯
- [ ] 免費額度設計過，確認它是「漏斗」而不是「終點站」
- [ ] 有至少一個不依賴主要金流系統的額外收入來源
