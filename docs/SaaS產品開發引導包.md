# SaaS 生產線
### 獨立開發者的出貨手冊 —— 以 Hookvox 真實上線經驗整理

> 這份手冊不是理論教科書，是把 Hookvox 從發想到上線、踩過的每一個坑，整理成可以直接照著走的流程。適合一人團隊、沒有工程背景但願意動手、想把自己的專業知識或工作流程做成一個真正能收錢的產品的人。

---

## 為什麼要有這份手冊

大部分「怎麼做 SaaS」的教學都停在「選好 stack、串好 Stripe」就結束了。但真正決定一個獨立開發者能不能活下來的，是後面那 80%：金流 webhook 半夜掛掉、使用者付了錢方案沒更新、額度設計不一致讓客訴爆炸、admin 後台一個 API 壞掉整頁白畫面。

這份手冊把整個流程拆成 5 個階段，每個階段都附上「真實踩過的坑」和「可直接勾選的 checklist」。

---

## 五個階段總覽

| 階段 | 核心問題 | 產出 |
|---|---|---|
| 01 產品發想與市場驗證 | 有沒有人已經在土法煉鋼做這件事，且願意付錢？ | 一個被驗證過的付費假設 |
| 02 技術架構與開發 | 一人團隊怎麼選 stack 才不會被自己絆倒？ | 可上線的最小可行產品 |
| 03 金流與訂閱系統 | 錢怎麼收、訂閱狀態怎麼跟金流同步？ | 穩定的收費系統 |
| 04 上線後維運與除錯 | 半夜出事時，你怎麼在 10 分鐘內知道發生什麼事？ | 一套排查 SOP + admin 工具 |
| 05 行銷與銷售 | 怎麼把流量變現，怎麼賣周邊商品？ | 持續成長的收入來源 |

## Phase 01 — 產品發想與市場驗證

### 核心原則

不要驗證「這個功能酷不酷」，要驗證「有沒有人正在用土法煉鋼的方式做這件事，而且願意為了省下那些時間付錢」。

Hookvox 的起點不是「AI 可以分析爆款影片」，而是「內容創作者每天花 2-3 小時手動拆解別人的爆款影片、抄筆記、找套路」。這個痛點本來就存在，AI 只是把它自動化。

### 找題目的方法

1. **從自己的重複性工作找**：你每週有沒有某件事一直手動重複在做？那就是候選題目。
2. **從垂直領域的「土法煉鋼」找**：觀察某個社群（IG、LINE 社群、Facebook 社團）裡的人在互相教什麼「手動流程」，那個流程就是你可以自動化的東西。
3. **從你自己願意先付費的東西找**：如果連你自己都不會為這個東西付錢，不要做。

### 驗證手法（照順序做，不要跳過）

- [ ] 找 5-10 個目標客群做訪談，問「你現在怎麼解決這個問題」，不要問「你會不會想要一個 AI 工具」
- [ ] 用最土的方式（Google 表單 + 人工處理）先手動服務 3-5 個真實客戶，確認他們真的願意付錢
- [ ] 在既有社群（LINE 群、IG）先用「手動版」測試付費轉換率，再決定要不要開發
- [ ] 定義清楚「免費版」和「付費版」的邊界在哪裡 —— 這會直接影響後面的額度設計

### 這階段最容易犯的錯

> 還沒驗證付費意願，就先把整套訂閱系統、金流串接都做好了。先驗證「人會不會付錢」，再花時間做「怎麼收錢」。

## Phase 02 — 技術架構與開發

### Stack 選擇邏輯（一人團隊版本）

Hookvox 用的組合：**Next.js + Supabase + Prisma + Vercel**。選擇邏輯不是「這是最潮的 stack」，是「一個人要維護前後端、資料庫、部署、金流，這個組合能把維運面壓到最低」。

| 元件 | 選擇 | 為什麼 |
|---|---|---|
| 前後端框架 | Next.js (App Router) | 前後端同一個 repo，API Route 直接當後端用，不用另外管一台 server |
| 認證 + 資料庫 | Supabase | Auth、Postgres、Storage 全部託管，不用自己維運資料庫 |
| ORM | Prisma | 型別安全，Schema 變更有版本控制，減少手寫 SQL 出錯機率 |
| 部署 | Vercel | Git push 自動部署，Serverless Functions 免運維，有 Cron Job 可以排程 |

### 架構鐵律

1. **先求「能動」，不要一開始就微服務化**：一人團隊沒有本錢維護多個服務，Monolith（單體應用）在成長到需要拆分之前都是對的選擇。
2. **AI 功能一定要做模型分級**：不是每個功能都要用最貴的模型。Hookvox 把「分析」用比較貴的模型、「生成」類任務下放到便宜模型，同樣的產出但成本差好幾倍。
3. **善用 Prompt Caching**：重複性高的 system prompt 開快取，長期使用下來 API 成本差異非常大。
4. **Serverless 的逾時限制要記住**：Vercel 預設 function 執行時間有上限，AI 分析類的長任務要單獨拉長 `maxDuration`，並且前端要能處理逾時（不要讓使用者以為當機了）。

### Checklist

- [ ] 決定好一套「一人也扛得住」的 stack，不要為了嘗鮮選太多陌生技術
- [ ] 資料庫 schema 設計時，把「使用者」「訂閱狀態」「訂單紀錄」拆成三張獨立的表（原因見 Phase 03）
- [ ] AI 功能依成本分級使用模型，不要無腦全部用最貴的
- [ ] 長任務（分析、生成）的逾時設定要跟前端錯誤訊息對齊，不要丟出使用者看不懂的技術錯誤
- [ ] 手機網路環境下的錯誤處理要單獨測試（空回應、逾時、非 JSON 回應都要有對應的使用者訊息）

## Phase 03 — 金流與訂閱系統

這是整份手冊裡「地雷密度最高」的章節。台灣本地 SaaS 產品幾乎一定會用到本土金流（綠界 ECPay 或藍新 NewebPay），這裡的坑比任何技術文件寫的都多。

### 資料模型：Order 與 Subscription 一定要分開

一個常見的新手錯誤是把「訂單」和「訂閱狀態」存在同一張表。正確做法：

- **Order（訂單）**：每一筆交易的不可變紀錄（誰、買什麼方案、金額、狀態、金流回傳的交易編號）
- **Subscription（訂閱）**：使用者「目前」的方案狀態（現在是什麼方案、什麼時候到期）

為什麼要分開？因為 Webhook 可能會失敗、可能會重送、使用者可能會重複付款。如果只有一張表，你沒辦法在 Webhook 失敗後去「回溯」使用者到底有沒有真的付過錢。

### Webhook 是最大地雷區 —— 四個一定要做的事

Webhook 是金流系統跟你的系統之間的橋，一旦這座橋斷了，使用者付了錢但方案沒更新，客訴會排山倒海而來。

1. **每個處理階段獨立 try/catch，不要讓整個 handler 共用一個 catch**
   驗證簽章、解密、JSON 解析、寫入資料庫，這四個步驟任何一個都可能單獨出錯。如果全部包在同一個 try/catch，你只會看到「處理失敗」，不知道到底是哪個階段壞的。

2. **把每一次 Webhook 呼叫都記錄到獨立的稽核表**
   包含：是否成功、失敗在哪個階段、失敗訊息、原始回傳內容。這張表是你半夜出事時唯一能看懂發生什麼事的地方。

3. **做冪等性（idempotency）檢查**
   金流服務商可能會重送同一筆通知。處理前一定要先檢查這筆交易是否已經處理過，否則會重複加值、重複發通知信。

4. **加解密資料一定要做容錯**
   本土金流的加解密機制（AES-256-CBC + Hash 驗證）對 Key/IV 的格式非常敏感。真實案例：因為環境變數尾端多了一個看不見的空白字元，導致解密全部失敗，錯誤訊息只會顯示 `bad decrypt`，完全看不出真正原因。解密函式應該要：
   - 對 Key/IV 做 `.trim()`
   - 驗證 Key/IV 長度是否正確，長度不對要提早丟出明確錯誤（而不是等到解密才失敗）
   - 解密失敗時記錄診斷資訊（資料長度、前綴字元），不要只記錄一句「解密失敗」

### 表單資料的隱藏陷阱

如果你用 `formData.get()` 讀取金流回傳的加密資料，要注意 `application/x-www-form-urlencoded` 格式會把 `+` 號解碼成空白字元。如果加密後的資料剛好含有 `+`，會被悄悄改成空白，導致解密永遠失敗，而且完全看不出問題出在哪。

### 額度與方案設計

- **免費額度是漏斗，不是慈善**：免費方案的次數限制要設計成「剛好讓使用者感受到價值，但不夠用到需要升級」，太多會讓人沒有升級動力，太少會讓人根本感受不到產品價值就流失。
- **所有頁面顯示的額度數字要單一來源**：Landing Page、方案頁、後台顯示的額度數字，一定要來自同一個設定檔，不要在多個地方各自寫死數字 —— 真實案例：某方案的額度在程式碼裡是 150，但所有前台頁面都顯示 200，導致使用者投訴「明明說 200 為什麼扣到 150 就不能用」。

### Checklist

- [ ] Order 和 Subscription 分成两張表，且有辦法從 Order 回溯 Subscription 狀態
- [ ] Webhook 的每個處理階段（驗證簽章、解密、解析、寫入）都有獨立錯誤處理與記錄
- [ ] Webhook 有冪等性檢查，同一筆交易不會被重複處理
- [ ] 加解密函式對 Key/IV 做過 trim 與長度驗證
- [ ] 有一個獨立的稽核表記錄所有 Webhook 呼叫，包含失敗原因
- [ ] 有 admin 工具可以在 Webhook 失敗時手動同步使用者訂閱狀態
- [ ] Notify URL / Return URL 沒有多餘的斜線或參數問題（本土金流對 URL 格式非常嚴格，多一個斜線可能導致 308 轉址失敗）
- [ ] 所有頁面顯示的額度/價格數字來自同一個設定檔，沒有寫死在多處

## Phase 04 — 上線後維運與除錯

產品上線只是開始。真正決定使用者留不留下來的，是出事的時候你多快能處理。

### Admin 後台是儀表板，不是奢侈品

一人團隊常常把 admin 後台放到最後才做，甚至跳過不做。這是錯的。沒有 admin 後台，你連「這個使用者到底有沒有付款成功」都要去資料庫手動查 SQL。

Admin 後台至少要有：

- 使用者查詢（用 email 或 ID 找到人，看到他目前的方案、額度使用狀況、付款紀錄）
- 手動同步訂閱工具（當 Webhook 失敗時，能一鍵把訂單狀態同步回訂閱狀態）
- 稽核紀錄（誰在什麼時候對這個使用者做了什麼操作）

### 前端錯誤處理：一個 API 掛掉不該讓整頁死掉

如果一個頁面要平行呼叫 4 個 API 才能組成完整畫面（例如 admin 頁面要同時抓使用者摘要、備註、稽核紀錄、額度調整紀錄），用 `Promise.all` 的話，任何一個 API 失敗，整頁都會白畫面。應該用 `Promise.allSettled`，讓每個區塊獨立顯示成功或失敗，不要讓一個次要功能拖垮整個頁面。

### 免費的除錯工具：資料庫的 Table Editor

不需要額外架設 log 系統。Supabase（或任何託管資料庫服務）內建的 Table Editor 就可以直接看到：

- 稽核表裡每一筆失敗的原因
- 資料庫裡的真實狀態，跟前端顯示的是否一致

當使用者說「我付款了但沒有生效」，第一步永遠是去稽核表查那筆交易的處理紀錄，不要用猜的。

### 建立自己的排查 SOP

當客訴「付款了但沒生效」進來時，照這個順序查：

1. 去金流服務商後台查這筆交易的狀態是否為「成功」
2. 去自己系統的 Webhook 稽核表查有沒有收到這筆交易的通知
3. 如果沒收到通知或處理失敗，查失敗訊息在哪個階段（驗證簽章？解密？寫入資料庫？）
4. 用 admin 工具手動同步該使用者的訂閱狀態，讓他先能用
5. 修復根本原因，避免下一個使用者遇到同樣的問題

### Checklist

- [ ] Admin 後台有使用者查詢、手動同步、稽核紀錄三項基本功能
- [ ] 前端平行請求用 `Promise.allSettled`，避免單點失敗拖垮整頁
- [ ] 建立好「付款未生效」的標準排查 SOP，不用每次都重新想一遍
- [ ] 定期（至少每週）檢查 Webhook 稽核表，主動抓出失敗但使用者還沒抱怨的個案
- [ ] 手機網路環境下的逾時、空回應都有專屬的、使用者看得懂的錯誤訊息

## Phase 05 — 行銷與銷售

### 早期通路：從既有信任關係開始

不要一開始就砸錢投廣告。先從你已經有信任關係的地方開始：LINE 社群、IG 帳號、既有客群。這些通路轉換率遠高於冷流量。

### 定價心理學

- **早鳥優惠製造急迫感**：限時、限量的優惠比「長期折扣」更能促成當下決定。
- **方案分級對應真實使用情境**：不要只做「便宜版」跟「貴版」兩級，中間一定要有一個對大多數人剛好夠用的主力方案。
- **免費試用額度是產品的第一個轉換漏斗**：額度設計參考 Phase 03。

### 用周邊商品增加營收來源、分散風險

如果你的核心產品依賴單一金流服務商，多一個獨立的收入來源（例如電子書、課程）除了增加營收，也能在金流出狀況時，證明你的業務不是只靠那一個管道 —— 這對客服溝通、對外說明都有幫助。

實作上：

- 電子書可以直接用金流服務商提供的「快速結帳連結」，不需要自己開發付款流程
- 在既有產品的多個頁面（首頁、帳單頁、Dashboard）用一致但不干擾主流程的方式露出，讓有需求的使用者自然看到

### Checklist

- [ ] 第一波客戶來自你已經有信任關係的通路，不是冷启動廣告
- [ ] 方案定價有清楚的早鳥/限時邏輯
- [ ] 免費額度设計過，確認它是「漏斗」而不是「終點站」
- [ ] 有至少一個不依賴主要金流系統的額外收入來源
- [ ] 周邊商品的曝光位置經過設計，不干擾主要付費轉換流程

## 總結：一頁式出貨 checklist

上線前，把這份手冊的 checklist 全部再過一次：

**產品驗證**
- [ ] 已用最土的方式驗證過付費意願
- [ ] 免費版/付費版邊界清楚

**技術**
- [ ] Stack 選擇符合一人維運能力
- [ ] AI 功能有做成本分級
- [ ] 長任務逾時處理完整

**金流**
- [ ] Order / Subscription 分表設計
- [ ] Webhook 各階段獨立錯誤處理 + 稽核記錄
- [ ] 冪等性檢查到位
- [ ] 加解密做過容錯與診斷

**維運**
- [ ] Admin 後台三大基本功能到位

- [ ] 定價策略清楚
